# IE 动作分析（现场作业视频 → 问题项 → 改善报告 → 流程程序图）

## Overview

把一段生产现场作业视频转化为一套可直接用于改善评审的 IE 交付物：按时间顺序拆分的动作清单、动素与价值分类、浪费点诊断、ECRS 改善建议，以及标准化的《问题项检查表》和《流程程序图》。

核心方法链：**视频抽帧 → 逐帧动作拆分 → 动素/符号/价值分类 → ECRS 与动作经济原则诊断 → 结构化数据 → 标准表单 + 改善报告 + 可视化流程程序图**。

## When to Use

- 用户提供现场作业视频（装配、焊接、机加、打压、打磨、搬运、检验等），要求分析动作、找浪费、提改善。
- 用户要求输出《动作分析问题项检查表》《流程程序图》或类似 IE 标准表单。
- 用户要求基于视频给出 ECRS 改善建议或动作经济原则分析。
- 用户没有视频但有文字描述的作业步骤，也可按本技能的方法论输出标准表单（跳过抽帧步骤）。
- 用户要求测工时、算标准工时、做秒表法、做工作抽样时（触发 Step 2.5 工时测量模块）。
- 用户要求做产线平衡、算 Takt、画 Yamazumi、做 Spaghetti、算 OEE、分析换型时（触发产线平衡模块）。

## 模块加载规则

- **动作分析（默认）**：Step 1–4 + 6–7，必读 `ie-toolkit.md`、`flow-chart-standard.md`、`output-schema.md`
- **工时测量（可选）**：Step 2.5，必读 `work-measurement.md`（秒表法 + Niebel N' + 绩效评估 + 标准工时 + 工作抽样）
- **产线平衡（可选）**：Step 6 扩展输出，必读 `line-balance.md`（Takt + 产线平衡 + SWCT + Yamazumi + Spaghetti + OEE + SMED + SLP）
- **红旗自检（交付前）**：按场景加载 `red-flags.md` 对应组（A=动作分析 / B=工时测量 / C=产线平衡）

## Workflow Decision Tree

```
用户给视频？
├─ 是 → Step 1 抽帧 → Step 2 拆分动作 → Step 3 分类 → Step 4 诊断 → Step 5 数据 → Step 6 交付
└─ 否（只有文字步骤）→ 直接 Step 3（据描述补时间/距离/符号）→ Step 5 → Step 6
用户给了填好的表单？→ 先读取表单，按表单字段回填，再补充改善建议
```

## Step 1 — 视频抽帧与变化点检测

**前置**：读 `references/filming-guide.md` §1 拍摄纪律，确认视频满足拍摄要求（固定三脚架、俯拍、≥5 个完整循环、1080p、整个作业区域在画面内）。不满足时提示用户补拍，不要硬猜。

先确认用户是否指定了分析起点（如"从拿料开始""前面调整设备不算"）。**指定了起点就必须用 `--start` 只抽目标段落**，不要全视频抽帧再人工跳过——全视频抽帧既浪费抽帧时间，又会把调整设备、空转等无关片段混进 contact sheet，干扰动作拆分判断。

运行抽帧脚本，生成按时间序列排列的帧图、缩略图拼图（contact sheet）和清单：

**先 ffprobe 探测视频时长**（抽帧前必做，决定 fps 和总帧数）：

```bash
ffprobe -v quiet -print_format json -show_format -show_streams "视频.mp4" 2>/dev/null | python -c "import sys,json; d=json.load(sys.stdin); f=d['format']; s=[x for x in d['streams'] if x['codec_type']=='video'][0]; print(f'Duration: {float(f[\"duration\"]):.1f}s'); print(f'Resolution: {s[\"width\"]}x{s[\"height\"]}'); print(f'FPS: {s[\"r_frame_rate\"]}')"
```

```bash
python scripts/extract_frames.py --video "视频路径.mp4" --out "输出目录/frames" --fps 2 --cols 4
```

- 用户指定起点时：`--start <秒>`（不确定精确秒时，先粗抽全视频低帧率定位起点帧号，再用 `--start/--end` 精抽目标段）。`--start` / `--end` 只截取关键时间段，可反复用于不同精度。
- `--fps` 建议：常规分析 1–2 fps；快速手工动作 3–5 fps；用户要求"每帧"时尽量提高（脚本逐帧导出）。
- **帧数过多时（>100 帧）用 delegate_task 并行分析**：把 contact sheets 分批（每批 4 张）交给多个子代理并行查看，每个子代理返回动作时间线，最后汇总。不要逐张串行看——26 张 sheet 串行要 26 轮工具调用，并行 6-8 个子代理一轮搞定。子代理 prompt 要写清：帧号范围、时间戳范围、设备/场景描述、要求输出逐帧动作 + 时间线汇总。
- 脚本输出：`frames/frame_*.jpg`、`contact_sheets/sheet_*.jpg`、`manifest.json`（含每帧时间戳）。
- 抽帧后用 `ViewImage` **逐张查看 contact sheet**（不是只看第一张），建立"时间 → 动作"的直观印象。
- **contact sheet 文件名是零填充三位数**：`sheet_001.jpg`、`sheet_002.jpg`，不是 `sheet_0.jpg`。传错路径会报 file not found。
- **vision_analyze 传本地文件用正斜杠 Windows 路径**：`C:\Users\...` 格式，不要 bash 的 `C:/Users/...` 格式（vision_analyze 不走 MSYS 路径转换）。
- 若动作边界不清，运行变化点检测辅助定位：

```bash
python scripts/detect_changes.py --manifest "输出目录/frames/manifest.json" --top 40
```

该脚本按相邻帧像素差异给出候选变化点及强度，帮助确定动作起止时刻；它只是辅助，最终判定以实际观看画面为准。

环境说明：脚本按 ffmpeg → OpenCV → imageio 顺序自动选择后端。若三者都不可用，会提示安装（优先 `pip install opencv-python-headless`，其次 `pip install imageio-ffmpeg`），**不要跳过这一步直接臆测视频内容**。抽帧脚本本身只依赖 ffmpeg，可在 build_report 之前先行；`build_report.py` 硬依赖 openpyxl，若报错 `需要 openpyxl` 先 `python -m pip install openpyxl` 再重跑。

## Step 2 — 逐帧动作拆分（As-Is）

逐帧/逐段观看，按时间顺序把连续画面切分为一个个"动作单元"，每个单元记录：

| 字段 | 含义 |
|---|---|
| 序号 | 从 1 递增，与流程程序图行号一致 |
| 作业内容 | 动宾短语，如"取 KBK 吊具""用检验工装检验""喷防溅剂" |
| 起始/结束帧 | 或起止秒数，便于复核 |
| 时间（秒） | 该动作持续时间，来自时间戳差值 |
| 搬运距离（m） | 仅搬运类动作填写，其余留空 |
| 动素 | 18 动素之一，见 `references/ie-toolkit.md` |
| 符号 | 操作/搬运/暂存/检查/储存 五选一 |
| 价值分类 | 有价值/无价值/无价值但必须 三选一 |

拆分原则：
- 同一目的、同一身体部位、连续完成的操作合并为一个单元；动作目的改变、拿取/放下物体、转身、走动时切分。
- 时间以画面时间戳为准，不用主观估计；总时长应与视频时长基本吻合。
- 搬运类动作必须尽量量出距离（可用视频中已知尺寸的物体如工装、工件按比例估算，并注明"估算"）。
- 详细判定规则见 `references/ie-toolkit.md`。

## Step 2.5 — 工时统计（可选模块）

当用户要求"测工时""算标准工时""做秒表法""做工作抽样"时，加载 `references/work-measurement.md` 并执行以下流程：

1. **定义问题**：新标准？验证宽放？审计产线平衡？确定置信度/精度（默认 95%/±5%）
2. **分解作业为元素**：在自然断点处切分，标注哪些是机器节拍（锁定 100% 不评级）
3. **计算样本量**：先测 10–20 个 pilot，用 Niebel N' 公式算正式样本量
   - `N' = [(40·√(N·Σx² − (Σx)²)) / Σx]²`（对方差最大的元素）
4. **收集数据**：多操作员/多班次，避免系统性偏差
5. **筛异物 + 逐元素评级**：
   - 异物排除标准：均值 ±3σ 或有可归因原因（设备卡料、中断、缺料等），每条排除必须记录原因和阈值
   - 绩效评估用 Westinghouse 四维度（技能/努力/条件/一致性），逐元素评估，机器节拍锁定 100%
6. **计算 OT → NT → ST**：
   - OT = 保留循环均值
   - NT = OT × 绩效评级（逐元素）
   - ST = NT × (1 + PFD 宽放)
7. **与现行标准对比**：差异超出置信度时，带数字写差异报告，提交标准负责人

**交付物是站得住的数字 + 现状是否合理的论证**，不是组织变更决策。

## Step 3 — IE 分类与价值判定

对每个动作单元完成三重分类：

1. **动素（Therblig）**：从 18 动素中选取最主要的一个，见 `references/ie-toolkit.md`。
2. **流程符号**：操作○ / 搬运→ / 暂存Ｄ / 检查□ / 储存▽。
3. **价值性**：有价值◎ / 无价值● / 无价值但必须○。判定口径：改变产品形状、性能、装配关系且客户愿付费的为有价值；搬运、寻找、等待、转身、清理飞溅、翻面、反复定位等为无价值；必要的检验、必要的搬运等归为"无价值但必须"。

统计三类价值占比，作为现状分析的核心数字。

## Step 4 — 浪费诊断与改善建议

对每一个"无价值●"或"无价值但必须○"动作，以及高耗时、高重复、高体力的有价值动作，做两层分析：

1. **ECRS 四原则**（按 E→C→R→S 顺序尝试，优先取消）：取消 Eliminate / 合并 Combine / 重排 Rearrange / 简化 Simplify。
2. **动作经济原则**：按身体使用、工作地布置、工具设备、物料搬运四类逐条对照，见 `references/ie-toolkit.md`。

每个问题项输出：问题描述（含时间/频次/距离证据）→ ECRS 类别 → 具体改进建议（可落地，如"引入旋转工作台""导入定位工装""合理布局按加工流程排布工序""低飞溅焊机引入"）→ 预期收益（节省时间/降低疲劳/减少搬运距离）。

常用改善对策库见 `references/ie-toolkit.md`，避免空泛建议。

## Step 5 — 生成结构化数据

按 `references/output-schema.md` 的字段定义，把 Step 2–4 的结果整理为一个 JSON 文件（模板见 `assets/analysis_template.json`）。字段必须齐全，`symbol` / `value` / `ecrs` 使用规定代码，以便脚本正确统计和绘制符号列。

信息不全时（如无产品名称、责任人），用"待补充"占位，不要编造数据；时间/距离等量化值必须来自视频观察或明确标注为估算。

## Step 6 — 生成交付物

运行生成脚本，一次性产出标准表单和可视化报告：

```bash
python scripts/build_report.py --data "分析数据.json" --out-dir "输出目录" --name "作业名称"
```

产出（仅两个文件，不生成 MD）：

1. `<作业名称>_动作分析表单.xlsx` —— 两个工作表：
   - **问题项检查表**：标题、基本信息、12 列问题项（A-L）、签批栏，严重度红/黄/绿色标，交替行底色，A4 横向打印；
   - **流程程序图**：数据区 19 列（B-T）+ U 列图例——序号/作业内容/搬运距离/时间 + 五符号列（F-J）+ 三价值列（K-M，绿/红/黄色标）+ 问题描述（N）+ ECRS 四列（O-R，蓝色标记）+ 改进建议（S）+ 备注（T）。合计行含 D/E 列 SUM 公式 + 符号/价值/ECRS 共 12 类计数，A4 横向打印。列结构以 `references/flow-chart-standard.md` 为准。
2. `<作业名称>_流程程序图.html` —— 完整 IE 分析报告（浏览器直接打开），7 个章节：
   - 一、现状分析（价值占比表 + 符号统计 + 现状结论）
   - 二、问题项清单（含严重度着色）
   - 三、浪费诊断与动作经济原则对照
   - 四、改善建议（按 ECRS 分类，彩色标签）
   - 五、预期效果
   - 六、结论
   - 七、流程程序图明细（动作表，符号着色 + 价值着色 + ECRS 标记）

**可选扩展输出**（用户要求时）：

注意：`build_report.py` 只生成上述 xlsx 表单 + 7 章 HTML 报告，**不自动产出**下列扩展内容。这些参考文件提供方法与计算口径，需要分析人员按文档计算后，以新章节追加到 HTML 报告，或另出交付物。不要向用户暗示脚本会自动生成。

- 用户要求"算 Takt""做产线平衡""画 Yamazumi""做 Spaghetti"时，加载 `references/line-balance.md`，按文档计算并追加：
  - Takt 时间计算 + 产线平衡分析（RPW 分配、产线效率、理论最少工位数）
  - SWCT 标准工作组合表（手动/自动/行走 vs Takt）
  - Yamazumi 平衡图（各工位柱子 vs Takt 线）
  - Spaghetti 移动路径图（操作员/物料路径 + 交叉点标注）
  - OEE 分解（可用率 × 性能率 × 合格率）
  - SMED 换型分析（内部/外部拆分 + 转外部建议）
- 用户要求"测工时""算标准工时"时，加载 `references/work-measurement.md`，在 HTML 报告中追加：
  - 样本量验证（N' 计算 + 是否充足）
  - 绩效评估记录（逐元素 Westinghouse）
  - 标准工时计算（OT → NT → ST 公式链 + 数值）
  - 异物排除日志
  - 工作抽样结果（如适用，带置信区间）

脚本输出的列结构与 `assets/动作分析问题项及改善表单模板.xlsx`（19 列数据 + U 列图例，由脚本生成的空白模板）完全一致；如用户提供已填表单，读取其中的实际字段值填入 analysis JSON，再交由脚本重新生成，不要直接改动输出 xlsx 的列布局。

**xlsx 外观美化（用户偏好，交付前默认执行）**：build_report.py 输出的是功能正确的素表，用户要求"外观看上去更好"时，必须做二次样式增强，**改完必须渲染成图用 vision 验收**（同指导书满铺的验证标准，不能只改参数就交付）：

1. 统一字体微软雅黑；标题 16pt 深蓝加粗居中；表头钢蓝底（#2E75B6）白字 9pt + 中粗上/下边框。
2. 严重度列条件着色：高=红底红字（#FFC7CE/#9C0006）、中=黄底黄字（#FFEB9C/#9C6500）、低=绿底绿字（#C6EFCE/#006100）。
3. 价值列着色：有价值=绿、无价值=红、无价值但必须=黄；ECRS 列有值时浅蓝高亮（#BDD7EE）。
4. 数据行交替浅灰底（#F2F2F2）；信息栏标签右对齐加粗+底部细分隔线；签字栏浅蓝底+中粗上边框。
5. 列宽按内容定（长文本列给足宽度避免换行撑高行高）；A4 横向、fitToPage、水平居中、窄边距。
6. **单位核对**：流程程序图"作业时间"表头单位必须与实际数据一致——单动作时间是秒时表头写 (S) 不写 (min)，交付前逐项核对合计。
7. **脚本即标准**：`build_report.py` 的列布局、`references/flow-chart-standard.md` 与 `assets/动作分析问题项及改善表单模板.xlsx` 三者必须一致，模板由脚本生成。列结构变更时改脚本后用测试数据重新生成模板，不要手动改输出 xlsx 的列布局。改完脚本后跑一遍端到端生成 + 渲染验收。

**渲染验收链路（Excel COM → PDF → PNG → vision）**：
- PowerShell 里 `Workbooks.Open` 传中文路径会乱码失败——先把 xlsx 复制成 ASCII 文件名（如 `ie_form.xlsx`）再渲染。
- PS 脚本用 bash heredoc（`cat > render.ps1 << 'EOF' ... EOF`）写文件，别在 python 里用 f-string 拼 PS 变量（`$ws.Index` 会被 Python 吃掉）。
- `ExportAsFixedFormat(0, pdfPath)` 逐 sheet 导出，再 `fitz`（PyMuPDF）转 200dpi PNG，逐张 `vision_analyze` 检查：对齐、配色、边框、截断。有问题就回改样式再渲染，直到 vision 确认无硬伤。
- 环境无 openpyxl/pip 时：先 `python -m ensurepip` 再 `python -m pip install openpyxl pymupdf`。

## Step 7 — 交付与质检

### 7.1 交叉验证（首次分析必做）

读 `references/filming-guide.md` §2，执行交叉验证：
- 手动计时 3 个完整循环，逐元素记录
- 与分析结果逐元素对比，接受门 ±5%
- 不通过 → 排查（§2.2）→ 重新分析或重拍
- 验证记录写入改善报告（§2.3 格式）

### 7.2 红线检查

读 `references/filming-guide.md` §3，确认：
- 视频未上传外部
- 报告不含操作员可识别姓名/工号（用"操作员A/B"代替）
- 分析结果仅用于工艺改善
- 原始视频已删除（报告确认后）

### 7.3 红旗自检

按场景加载 `references/red-flags.md` 对应组：

**动作分析（A 组）**：
- 动作序号连续、时间/距离合计与明细一致；
- 每个无价值动作都有问题描述和改善建议；
- 符号列、价值列、ECRS 列只填规定字符；
- xlsx 中合计公式为 `SUM`，HTML 中符号与 xlsx 一致；
- 报告中数字与表单一致；
- HTML 报告 7 章节完整（现状分析/问题项/浪费诊断/ECRS/预期效果/结论/明细）；
- 改善建议具体到"做什么、用什么设备/方法"，无空话；
- 无价值动作占比合理（< 15% 时复查价值判定标准）；
- 严重度判定执行了高/中/低标准（>60s 或安全相关 = 高）。

**工时测量（B 组）**（如执行了 Step 2.5）：
- 循环数 ≥ N' 要求；
- 异物排除有日志（原因 + 阈值）；
- 评级逐元素（非整循环一个分）；
- OT/NT/ST 三个数字未混用；
- 工作抽样带置信区间。

**产线平衡（C 组）**（如执行了扩展输出）：
- Takt 从需求算（非从循环时间）；
- 平衡到瓶颈周期时间（非平均）；
- 产线效率 ≥ 85%（低于则检查优先序约束）；
- 换型分析区分内部/外部。

用 `present_files` 展示 xlsx、html 两类成果（HTML 放第一位以便预览）。
